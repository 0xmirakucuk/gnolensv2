## 1. Architecture (whole app, M0 builds only the bold parts)

One Next.js monolith. No separate backend service until something forces it (long ingestion jobs in M4 are the likely first candidate).

```
Browser
  │
  ▼
Next.js (App Router, RSC)                       ── deployed as one app
  ├─ **app/(public)**    sign-in, check-email pages
  ├─ **app/(app)**       authenticated area: courses, (later) tests, dashboard
  ├─ app/admin           M1+: question bank, ingestion, review queue
  ├─ **app/api/auth**    auth route handler
  │
  ├─ **lib/db**          Prisma client singleton
  ├─ **lib/auth**        auth config, session helpers, domain check
  ├─ **lib/email**       one `sendMagicLink()` interface; SMTP (Mailpit) in dev, provider in prod
  ├─ **lib/env**         zod-validated env vars; app fails fast at boot if one is missing
  ├─ **lib/syllabus**    YAML schema (zod), loader, seed logic
  ├─ lib/mastery         M3: pure functions, unit tested
  ├─ lib/retrieval       M4: pgvector search over Chunk
  └─ lib/llm             M4: single provider-agnostic interface (spec rule)
  │
  ▼
PostgreSQL 17 + pgvector   (docker-compose locally; managed in prod)
```

Principles I'll hold to:
- **Server components read data directly** through small query functions in `lib/*`, no internal REST layer. Mutations use server actions. That keeps M0–M3 simple. An API layer can come later if a mobile client appears.
- **Taxonomy keys are stable slugs** (`micro`, `micro.u1`, `micro.u1.p1`). Questions (M1), mastery (M3) and chunks (M4) all hang off `Part`. So slugs from the YAML are the durable identity, and DB ids are internal.
- **Business rules live in `lib/`, not in pages.** Examples are the domain check, seed and mastery logic. That way Vitest can cover them without a browser.
- **Authorization is checked on the server, per request**, in the layout of the protected route group and in every server action. Middleware only handles the fast redirect and is not the security boundary.

## 2. Data model for M0

M0 creates only what M0 needs, plus `role`, because M1's admin editor needs it and adding it now costs nothing.

```prisma
enum Tier { FREE PRO }
enum Role { STUDENT ADMIN }

model User {
  id            String   @id @default(cuid())
  email         String   @unique          // stored lowercased
  emailVerified Boolean  @default(false)
  name          String?
  year          Int?                        // BEMACS year 1-3; null until onboarding (M1+)
  tier          Tier     @default(FREE)
  role          Role     @default(STUDENT)
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  sessions      Session[]
  accounts      Account[]
}
// Session, Account, Verification: exactly as Better Auth's Prisma schema generator emits them.

model Course {
  id     String @id @default(cuid())
  slug   String @unique          // "micro"
  name   String                  // "Microeconomics"
  code   String?                 // Bocconi course code, if you want it shown
  year   Int                     // 1
  order  Int
  units  Unit[]
}

model Unit {
  id       String @id @default(cuid())
  slug     String @unique        // "micro.u1"  (globally unique, prefixed by course)
  title    String
  order    Int
  courseId String
  course   Course @relation(fields: [courseId], references: [id], onDelete: Restrict)
  parts    Part[]
  @@unique([courseId, order])
}

model Part {
  id     String @id @default(cuid())
  slug   String @unique          // "micro.u1.p1"
  title  String
  order  Int
  unitId String
  unit   Unit @relation(fields: [unitId], references: [id], onDelete: Restrict)
  @@unique([unitId, order])
}
```

`onDelete: Restrict` is there because later milestones hang questions and mastery off `Part`. Deleting syllabus rows by accident must fail loudly.

## 3. Syllabus YAML format and seed

One file per course: `content/syllabus/<course-slug>.yaml`.

```yaml
slug: micro
name: Microeconomics
code: "30xxx"          # optional
year: 1
order: 1
units:
  - slug: u1
    title: Consumer choice
    parts:
      - slug: p1
        title: Preferences and utility
      - slug: p2
        title: Budget constraint
```

- The YAML uses short local slugs. The loader expands them to `micro.u1.p1`. `order` comes from list position.
- The file is validated with zod. Errors name the file and path, e.g. `micro.yaml: units[2].parts[0].title is required`.
- The seed (`pnpm db:seed`) is an **idempotent upsert by slug** inside one transaction. Running it twice changes nothing, and renaming a title updates the row in place.
- **The seed never deletes.** A slug in the DB that is missing from the YAML is reported as a warning ("orphaned: micro.u3.p2"). Removing it is a manual decision, because from M1 on it may have questions attached.
- Order swaps use a two-phase update so the `@@unique([unitId, order])` constraint doesn't trip mid-seed.

## 4. Auth flow

1. `/sign-in`: an email field.
2. Server normalizes the email (trim, lowercase) and runs `isAllowedEmail()`. Accept only an exact domain match on `studbocconi.it`. Reject subdomains, lookalikes (`studbocconi.it.evil.com`, `studbocconi.it@x.com`), and anything that doesn't parse as a single address. Rejected emails get a clear error and **no email is sent**. The same check runs again inside the auth hook so the API can't be called around the form.
3. The magic link is emailed. Expiry is 15 minutes and the link is single use (Better Auth defaults, set explicitly).
4. The first sign-in creates the `User` (`tier FREE`, `role STUDENT`).
5. The session cookie is httpOnly, secure in prod, 30-day rolling.
6. Admins come from an `ADMIN_EMAILS` env allowlist that sets `role = ADMIN` on sign-in (see Q3).
7. Sign-in is rate-limited per email and per IP. Better Auth has built-in limiting; I'll configure it so the form can't be used to spam students' inboxes.

## 5. Pages and layout

- `/` redirects to `/courses` when signed in and to `/sign-in` otherwise.
- `/sign-in` and `/sign-in/check-email` are public.
- `(app)/layout.tsx` does the server-side session check. It renders a top bar (app name, user email, sign-out) and a content container, and is responsive and dark-mode aware through shadcn defaults.
- `/courses` shows cards for the year-1 courses with unit and part counts.
- `/courses/[courseSlug]` shows units as an accordion with their parts listed. Parts aren't clickable yet; M2/M3 give them a destination.
- There's a `not-found` page for unknown course slugs.

## 9. Decisions I made myself (small, reversible)

- Route groups `(public)` / `(app)`, and query functions in `lib/courses/queries.ts` instead of an API layer.
- cuid ids. Slugs are the external identity for taxonomy.
- `role` added to `User` now, ahead of M1.
- Mailpit for local mail, with e2e reading magic links through its API. That avoids any test-only auth backdoor.
- Prisma pinned to the latest stable 7.x rather than the 8.0 RC that npm tags `latest`.
- Placeholder syllabus content is clearly marked `# PLACEHOLDER` until the real one is provided.

## 10. Questions for the owner

Blocking M0 (hard to reverse per CLAUDE.md):

1. **Auth library.** Is Better Auth (recommended, reasons above) OK? The alternative is Auth.js v5, which is still beta.
2. **Transactional email provider for production.** Students need real magic-link emails, and that's a paid or third-party service. Options are Resend, Postmark or AWS SES. Dev and CI use Mailpit either way, so this only blocks deploying, not building M0. It matters more than usual here: university mail servers (`studbocconi.it` is Microsoft 365, I believe) often quarantine link-only emails from new domains. We'll want a verified sending domain with SPF/DKIM/DMARC.
3. **Admin access.** Admins (you, content reviewers) probably don't all have `@studbocconi.it` addresses. Is an `ADMIN_EMAILS` env allowlist that bypasses the domain restriction OK, or must admins also use student emails?
4. **Hosting target** (Vercel + Neon/Supabase, Railway, Fly, a VPS…). It isn't needed to finish M0 locally, but it decides the Postgres provider, which must support pgvector, and whether M4's ingestion can run as a serverless function. Also, is there a domain name?

Needed for content, but not blocking the code:

5. **Real syllabus for the three courses.** What are the official course names/codes and their units and parts, or the course guides I should transcribe into YAML? Also, is "Mathematics" one course or split (e.g. Math 1 / Math 2 across semesters)? I'll use placeholders until then.
6. **Spec path.** CLAUDE.md says `docs/SPEC.md` but the file is at the repo root `SPEC.md`. Should I move it to `docs/SPEC.md` (my suggestion) or fix CLAUDE.md?
7. **`User.year`.** Should it be asked at first sign-in (a one-field onboarding), or left null until years 2–3 exist? My default is to leave it null in M0 and add onboarding when a second year is added.
8. **Deadline.** Do you have the first partial exam date yet? The spec lists it as setting the M0–M3 deadline, and it affects how much polish goes into each milestone.
9. **Product name.** The repo is `gnolensv2` and the spec says "BEMACS Exam Prep". Which name goes in the UI header and page titles?
10. **Privacy.** Beyond student emails, is there anything the app should *not* store? GDPR applies. I'm planning a minimal privacy note on the sign-in page and no analytics in M0.
